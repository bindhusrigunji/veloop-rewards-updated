## 5. User Engagement, Session Activity, Task Completion & Feature Adoption Analytics

### Data Separation & Current Repository Reality
- **Simulated Test Data (Currently Active in Sandbox):** None of the session, task-funnel, or feature-usage telemetry collections exist in the sandbox database. Only account registration timestamps (`User.createdAt`), `accountStatus === 'active'`, and ledger transaction timestamps (`WalletTransaction.createdAt`) are populated (`dataOrigin: 'SIMULATED_DEMO'`, `productionDataConnected: false`).
- **Actual Available Data:** `User.{userId, accountStatus, createdAt}` and completed reward events (`WalletTransaction.{userId, source, createdAt}` for `DAILY_REWARD`, `GAME_REWARD`, `AD_REWARD`) — **insufficient** to compute session-based engagement, retention, task abandonment, or general feature adoption.
- **Missing Production Integration Requirements (`Not Implemented`):** The current `/server/models/*.ts` codebase does **not** contain **`SessionLogs`**, **`TaskEvents`**, **`FeatureEvents`**, or even `User.lastLoginAt`. All proposed schemas below are future production integration requirements only and have **not** been implemented; no VELOOP engagement values are fabricated.

---

### 5.1 KPI-by-KPI Specification

#### 1. Daily Active Users (DAU)
1. **Business Meaning & Formula:** Measures unique users who actively opened or interacted with the application on a given calendar day (UTC or IST, pending stakeholder confirmation).  
   `DAU(date) = COUNT(DISTINCT SessionLogs.userId WHERE SessionLogs.startedAt BETWEEN dayStart AND dayEnd AND dataOrigin == 'production')`
2. **Required Source Fields & Events:** `SessionLogs.userId`, `SessionLogs.sessionId`, `SessionLogs.startedAt`, `SessionLogs.eventType` (`APP_OPEN` / `SESSION_HEARTBEAT`), `SessionLogs.dataOrigin`.
3. **Supported by Current Repository?** **No.** Neither `SessionLogs` nor `User.lastLoginAt` exists. (`GET /api/admin/analytics` reports `kpis.activeUsers` strictly from `User.accountStatus === 'active'`, which is account permission status, not DAU.)
4. **Current Limitations & Testability Status:** **Not Testable (`KPI-06`)**. Cannot proxy DAU from `WalletTransaction` alone because users who browse balances, view payout options, or fail/abandon tasks without earning rewards leave zero ledger rows.
5. **Required Future Schema / Event Tracking:** Introduce `SessionLogs` collection (`{ sessionId, userId, startedAt, endedAt, durationSec, platform, appVersion, dataOrigin }`) populated from authenticated client session start/heartbeat endpoints.

#### 2. Monthly Active Users (MAU)
1. **Business Meaning & Formula:** Measures distinct users who recorded at least one authenticated session within a trailing 30-day window (or calendar month).  
   `MAU(windowEnd) = COUNT(DISTINCT SessionLogs.userId WHERE SessionLogs.startedAt BETWEEN (windowEnd - 30d) AND windowEnd AND dataOrigin == 'production')`
2. **Required Source Fields & Events:** `SessionLogs.userId`, `SessionLogs.startedAt`, `SessionLogs.dataOrigin`.
3. **Supported by Current Repository?** **No.**
4. **Current Limitations & Testability Status:** **Not Testable (`KPI-07`)**. Lacks `SessionLogs` history and authentication session logs.
5. **Required Future Schema / Event Tracking:** Indexed time-series `SessionLogs` collection partitioned/indexed on `{ dataOrigin: 1, startedAt: -1, userId: 1 }` to support rolling 30-day distinct user aggregations.

#### 3. DAU / MAU Stickiness Ratio
1. **Business Meaning & Formula:** Quantifies habitual engagement frequency — the share of monthly active users returning on a typical day.  
   `Stickiness (%) = (DAU / NULLIF(MAU, 0)) * 100` (or `AVG(DAU over 30d) / MAU * 100`, pending stakeholder confirmation).
2. **Required Source Fields & Events:** Derived strictly from `DAU` and `MAU` (`SessionLogs.userId`, `SessionLogs.startedAt`, `SessionLogs.dataOrigin`).
3. **Supported by Current Repository?** **No.**
4. **Current Limitations & Testability Status:** **Not Testable (`KPI-08`)**. Blocked until both `DAU` and `MAU` are backed by real `SessionLogs` telemetry.
5. **Required Future Schema / Event Tracking:** `SessionLogs` ingestion plus pre-aggregated `DailyEngagementRollup` (`{ date, dau, mau, stickinessPct, dataOrigin }`) strictly separated between `simulated` and `production`.

#### 4. Day-7 and Day-30 Retention
1. **Business Meaning & Formula:** Percentage of a signup cohort (users registered on Day 0) who return for an active session on Day 7 or Day 30 after registration.  
   `Day-N Retention (%) = (COUNT(DISTINCT cohortUsers WITH session on Day N) / COUNT(cohortUsers registered on Day 0)) * 100`
2. **Required Source Fields & Events:** `User.userId`, `User.createdAt` (exists in current repo) joined with `SessionLogs.userId`, `SessionLogs.startedAt`, `SessionLogs.dataOrigin` (missing).
3. **Supported by Current Repository?** **Partially backed on denominator only (`User.createdAt` exists); numerator is NOT supported.**
4. **Current Limitations & Testability Status:** **Not Testable (`KPI-10`)**. Without daily `SessionLogs` or `ActivityLogs`, Day-7/Day-30 return visits cannot be measured.
5. **Required Future Schema / Event Tracking:** `SessionLogs` collection plus cohort attribution fields (`User.cohortDateUtc`, `User.dataOrigin`) and stakeholder confirmation on exact retention definition (exact Day-N vs rolling Day-N window).

#### 5. Session Count and Average Session Duration
1. **Business Meaning & Formula:** Measures total user engagement sessions in a window and mean active time spent per session.  
   `Session Count = COUNT(SessionLogs.sessionId WHERE startedAt IN window AND dataOrigin == 'production')`  
   `Average Session Duration (sec) = AVG(COALESCE(SessionLogs.durationSec, endedAt - startedAt) WHERE endedAt IS NOT NULL)`
2. **Required Source Fields & Events:** `SessionLogs.sessionId`, `SessionLogs.userId`, `SessionLogs.startedAt`, `SessionLogs.endedAt`, `SessionLogs.durationSec`, `SessionLogs.lastHeartbeatAt`, `SessionLogs.dataOrigin`.
3. **Supported by Current Repository?** **No.** Stateless JWT tokens are issued on login without storing session open/close timestamps or heartbeats.
4. **Current Limitations & Testability Status:** **Not Testable**. Current API logs HTTP requests transiently to console only; no persistent session lifecycle collection exists.
5. **Required Future Schema / Event Tracking:** `SessionLogs` schema capturing `SESSION_START`, periodic `SESSION_HEARTBEAT` (to bound duration when mobile apps are backgrounded/closed abruptly), and `SESSION_END` events.

#### 6. Task Completion Rate
1. **Business Meaning & Formula:** Share of initiated reward tasks (e.g., Daily Claim flow, Fortune Wheel spin, Ad Watch, Offerwall task, Referral step) that reach verified completion.  
   `Task Completion Rate (%) = (COUNT(TaskEvents WHERE status == 'COMPLETED') / NULLIF(COUNT(TaskEvents WHERE status IN ['STARTED','COMPLETED','ABANDONED','FAILED']), 0)) * 100`
2. **Required Source Fields & Events:** `TaskEvents.taskEventId`, `TaskEvents.taskId`, `TaskEvents.taskType`, `TaskEvents.userId`, `TaskEvents.status` (`STARTED`, `COMPLETED`, `ABANDONED`, `FAILED`), `TaskEvents.startedAt`, `TaskEvents.completedAt`, `TaskEvents.dataOrigin`.
3. **Supported by Current Repository?** **No.** Only completed outcomes exist as ledger credits (`WalletTransaction` with `source IN ['DAILY_REWARD','GAME_REWARD','AD_REWARD']`), with zero tracking of `STARTED` attempts.
4. **Current Limitations & Testability Status:** **Not Testable**. Missing `TaskEvents` makes the denominator (total tasks started) unknown, so completion rate cannot be calculated without inventing data.
5. **Required Future Schema / Event Tracking:** Dedicated `TaskEvents` collection logging every `TASK_STARTED`, `TASK_COMPLETED`, `TASK_FAILED`, and `TASK_ABANDONED` transition with `taskType`, `idempotencyKey`, and `linkedTransactionId`.

#### 7. Task Abandonment Rate
1. **Business Meaning & Formula:** Percentage of initiated reward tasks where the user exited, timed out, or failed to complete the required action after starting.  
   `Task Abandonment Rate (%) = (COUNT(TaskEvents WHERE status == 'ABANDONED') / NULLIF(COUNT(TaskEvents WHERE status == 'STARTED' OR uniqueStartedAttempts), 0)) * 100`  
   *(Alternatively `100 - Task Completion Rate (%) - Task Failure Rate (%)`, depending on stakeholder definition of timeouts vs explicit cancellations.)*
2. **Required Source Fields & Events:** `TaskEvents.taskEventId`, `TaskEvents.userId`, `TaskEvents.taskType`, `TaskEvents.status`, `TaskEvents.abandonReason`, `TaskEvents.abandonedAt`, `TaskEvents.dataOrigin`.
3. **Supported by Current Repository?** **No.**
4. **Current Limitations & Testability Status:** **Not Testable**. No `TaskEvents` schema or client abandonment/timeout instrumentation exists.
5. **Required Future Schema / Event Tracking:** `TaskEvents` collection with timeout sweep rules (e.g., marking uncompleted `STARTED` ad/offerwall sessions older than TTL as `ABANDONED`) and explicit funnel drop-off stage metadata (`dropOffStep`).

#### 8. Feature Adoption Rate
1. **Business Meaning & Formula:** Proportion of active users who meaningfully interact with a specific product feature (e.g., Fortune Wheel, Daily Reward, SVEs Staking, Payout Withdrawals, Referral Sharing) at least once (or N times) within a period.  
   `Feature Adoption Rate(feature, period) (%) = (COUNT(DISTINCT FeatureEvents.userId WHERE featureName == feature AND eventAction == 'USED' IN period) / NULLIF(MAU or Active Users IN period, 0)) * 100`
2. **Required Source Fields & Events:** `FeatureEvents.eventId`, `FeatureEvents.userId`, `FeatureEvents.featureName`, `FeatureEvents.eventAction` (`VIEWED`, `USED`, `COMPLETED`), `FeatureEvents.occurredAt`, `FeatureEvents.dataOrigin`, plus denominator from `SessionLogs` (`MAU` / `DAU`) or `User`.
3. **Supported by Current Repository?** **No.** While some transactional features leave indirect footprints (`WalletTransaction.source`, `Withdrawal`), non-ledger features (e.g., viewing transaction filters, opening Fortune Wheel without spinning, opening Payouts/Referrals pages, API Docs/Admin Analytics usage) are unlogged.
4. **Current Limitations & Testability Status:** **Not Testable**. Missing `FeatureEvents` telemetry and missing `SessionLogs` denominator prevent consistent cross-feature adoption measurement.
5. **Required Future Schema / Event Tracking:** Dedicated `FeatureEvents` collection (`{ eventId, userId, sessionId, featureName, eventAction, metadata, occurredAt, dataOrigin }`) combined with `SessionLogs` so every product feature can be measured consistently against true active user counts.

## 6. Implemented KPI Calculation Methods, Filter Logic & Validation Audit (All 46 KPIs)

### 6.1 Backend Aggregation Endpoints & Execution Flow
All executive analytics metrics are computed dynamically in Node.js TypeScript service/route modules from MongoDB/Mongoose collections (no separate batch worker or materialized analytics table exists):

1. **`GET /api/admin/analytics` (`/server/routes/adminRoutes.ts` $\rightarrow$ `AnalyticsService.getAdminAnalytics` in `/server/services/analyticsService.ts`):**
   - Loads `User`, `Wallet`, `WalletTransaction`, `Withdrawal`, `PayoutOption`, lifetime `COMPLETED` `WalletTransaction`, and `Referral` records in `Promise.all(...)`.
   - Returns all `27` Validated KPIs (`KPI-01`, `03`, `04`, `11`–`15`, `18`, `19`, `22`–`25`, `28`–`31`, `33`, `35`–`38`, `42`–`45`) plus the `3` existing confirmation-pending KPIs (`KPI-02`, `21`, `39`).
   - Enforces `status === 'COMPLETED'` on value/reward/trend/reconciliation metrics while evaluating `KPI-30` arithmetic integrity across all matched rows.
   - Cleanly separates **VEs** counts from **all-currency** counts and tags every response with `dataOrigin` and `dateFilter: { timezone: 'UTC', startDateUtc, endDateUtc }`.
2. **`GET /api/admin/referrals`**: Returns referral attribution list, conversion rate (`KPI-45`), and explicit `PENDING_BUSINESS_RULE` payout lock notice.
3. **`GET /api/admin/user-conflicts`**: Audits `User` and `Wallet` non-destructively for duplicate canonical emails, non-admin users missing wallets, and orphan wallets.
4. **`GET /api/wallet/summary` (`/server/routes/walletRoutes.ts`)**: Runs user-scoped MongoDB `$match` + `$group` pipelines on `WalletTransaction` filtering `status: 'COMPLETED'`.

### 6.2 Date Range & Query Filter Scope (`GET /api/admin/analytics`)
| Query Parameter | Applied To | Exact Code Behavior (`AnalyticsService.getAdminAnalytics`) |
| :--- | :--- | :--- |
| **`startDate`** | `WalletTransaction.createdAt`, `Withdrawal.requestedAt` | Date-only `YYYY-MM-DD` strings parse strictly as UTC `00:00:00.000Z` via `parseUtcDateBoundary(..., 'start')`. Ignored by `User`, `Wallet`, `PayoutOption`, `Referral`, and lifetime `KPI-31`. |
| **`endDate`** | `WalletTransaction.createdAt`, `Withdrawal.requestedAt` | Date-only `YYYY-MM-DD` strings parse strictly as UTC `23:59:59.999Z` via `parseUtcDateBoundary(..., 'end')`. Explicit ISO timestamps are preserved verbatim. |
| **`currency`** | `WalletTransaction.currency` | Lowercased when `!== 'ALL'`. Never counts non-`ves` transactions in `ves` totals/counts; does not filter `Wallet.walletLiability` or lifetime `KPI-31`. |
| **`source`** | `WalletTransaction.source` | Exact match when `!== 'ALL'`. Does not filter `Withdrawal`, `User`, or `Wallet`. |
| **`search`** | `WalletTransaction.{transactionId, userId, description, source}` | Regex-escaped case-insensitive `$regex` match on ledger transactions only. |
